# Lesson 3 — Dynamic Routes, Params and Search Params

## The problem

You can't create a folder for every blog post or product. You need one route definition that matches many URLs, and the page needs to know *which* URL matched. You also want:

- the popular ones prerendered at build time (fast and cheap),
- the rest rendered on demand,
- invalid ones to return 404,
- and all of it type-safe.

## How it works

### The three bracket forms

| Folder | Matches | `params` |
| --- | --- | --- |
| `app/blog/[slug]/page.tsx` | `/blog/a` | `{ slug: 'a' }` |
| `app/shop/[...slug]/page.tsx` | `/shop/a`, `/shop/a/b/c` (**not** `/shop`) | `{ slug: ['a','b','c'] }` |
| `app/docs/[[...slug]]/page.tsx` | `/docs`, `/docs/a`, `/docs/a/b` | `{ slug: undefined }` or `{ slug: [...] }` |
| `app/[category]/[item]/page.tsx` | `/shoes/nike` | `{ category: 'shoes', item: 'nike' }` |

Types (generated for you):

| Route | Type |
| --- | --- |
| `[slug]` | `string` |
| `[...slug]` | `string[]` |
| `[[...slug]]` | `string[] \| undefined` |

### `params` is a Promise (since v15)

```tsx
// app/blog/[slug]/page.tsx
export default async function Page({ params }: PageProps<'/blog/[slug]'>) {
  const { slug } = await params
  return <h1>{slug}</h1>
}
```

Why a Promise? It lets Next **start rendering before the params are known** and only wait at the point where you actually read them. With Cache Components and Partial Prefetching this is what makes a **static shell** possible for a dynamic route.

- `PageProps<'/route'>`, `LayoutProps<'/route'>` and `RouteContext<'/route'>` are **global** types. No import needed. They are generated by `next dev`, `next build` and `next typegen`.
- In a Client Component page you can't `await`, so use `use(params)`, or `useParams()` anywhere in the client tree.

### Narrow the type with runtime validation

`params` values are just strings, because users can type anything into the URL. Validate once and let TypeScript narrow the type:

```tsx
// app/[locale]/page.tsx
import { notFound } from 'next/navigation'

const LOCALES = ['en', 'am', 'fr'] as const
type Locale = (typeof LOCALES)[number]

function assertLocale(value: string): asserts value is Locale {
  if (!LOCALES.includes(value as Locale)) notFound()
}

export default async function Page(props: PageProps<'/[locale]'>) {
  const { locale } = await props.params // string
  assertLocale(locale)                   // now Locale
  // ...
}
```

This project already uses Zod (`src/shared/schemas/`), so `z.enum(LOCALES).safeParse(locale)` works just as well.

### ⚡ Dynamic routes under Cache Components

There are two modes, and the build enforces them.

**Mode 1: no `generateStaticParams`.** Param values are unknown at build time, so they are **runtime data**. Reading them must happen **inside `<Suspense>`** (or under a `loading.tsx`, which is a Suspense boundary). Next prerenders a **static shell** (everything outside the boundary) and streams the rest per request.

```tsx
// app/blog/[slug]/page.tsx
import { Suspense } from 'react'

export default function Page({ params }: PageProps<'/blog/[slug]'>) {
  return (
    <article>
      <BlogHeader />                                      {/* static shell */}
      <Suspense fallback={<PostSkeleton />}>
        <PostBody params={params} />                      {/* reads params */}
      </Suspense>
    </article>
  )
}

async function PostBody({ params }: Pick<PageProps<'/blog/[slug]'>, 'params'>) {
  const { slug } = await params
  const post = await getPost(slug)
  return <div>{post.content}</div>
}
```

Notice the trick: **the page doesn't await `params`.** It passes the *promise* down. This is the standard pattern for this project's config.

**Mode 2: with `generateStaticParams`.** You give Next sample values. At build time it renders each one and **validates** that the route doesn't access runtime APIs (`cookies()`, `headers()`, `searchParams`) outside Suspense. Listed params become static HTML. Unlisted params are rendered on the first request and then saved.

```tsx
// app/blog/[slug]/page.tsx
export async function generateStaticParams() {
  const posts = await getAllPostSlugs()
  return posts.slice(0, 50).map((slug) => ({ slug }))   // top 50 at build time
}

export default async function Page({ params }: PageProps<'/blog/[slug]'>) {
  const { slug } = await params
  const post = await getPost(slug)   // should be 'use cache' (Phase 04)
  return <article>{post.content}</article>
}
```

⚡ rules to remember:

- `generateStaticParams` **must return at least one item**. An empty array is a **build error** under Cache Components. If you truly don't know any values, return a placeholder such as `[{ slug: '__placeholder__' }]` and call `notFound()` for it. This weakens build validation, so use it sparingly.
- **`export const dynamicParams = false` is not available** with Cache Components. (Without Cache Components it would 404 every unlisted param.) To restrict values, validate and call `notFound()` instead.
- Build validation **only covers code paths the sample params hit.** If `slug.startsWith('private-')` takes a branch that reads `cookies()` without Suspense, the build passes and the first runtime request for `private-x` fails. Wrap such branches in `<Suspense>`.

### Multiple dynamic segments: bottom-up or top-down

For `app/products/[category]/[product]/page.tsx`:

```tsx
// Bottom-up: the page generates both params
export async function generateStaticParams() {
  const products = await getProducts()
  return products.map((p) => ({ category: p.categorySlug, product: p.id }))
}
```

```tsx
// Top-down: the layout generates the categories...
// app/products/[category]/layout.tsx
export async function generateStaticParams() {
  return (await getCategories()).map((c) => ({ category: c.slug }))
}

// ...and the page runs once PER category, receiving the parent params
// app/products/[category]/[product]/page.tsx
export async function generateStaticParams({
  params: { category },
}: { params: Awaited<LayoutProps<'/products/[category]'>['params']> }) {
  return (await getProductsIn(category)).map((p) => ({ product: p.id }))
}
```

Note: the `params` argument of `generateStaticParams` is **synchronous**, unlike the component prop. A segment can generate params for itself and segments **above** it, never below.

### `searchParams` (the query string)

```tsx
// app/products/page.tsx
export default function Page({ searchParams }: PageProps<'/products'>) {
  return (
    <>
      <Filters />                                   {/* static */}
      <Suspense fallback={<GridSkeleton />}>
        <ProductGrid searchParams={searchParams} />
      </Suspense>
    </>
  )
}

async function ProductGrid({ searchParams }: Pick<PageProps<'/products'>, 'searchParams'>) {
  const { q, page = '1' } = await searchParams       // values: string | string[] | undefined
  const products = await searchProducts(String(q ?? ''), Number(page))
  return <Grid items={products} />
}
```

- Only **pages** receive `searchParams`. Layouts don't (Lesson 2).
- Reading `searchParams` makes that part **request-time**, so it must be inside Suspense under ⚡.
- Values can be `string | string[] | undefined` (`?tag=a&tag=b` gives an array). Always normalize them. A Zod schema is good for this.

When to use which:

| Need | Use |
| --- | --- |
| Load data on the server based on the query (filters, pagination) | `searchParams` prop on the page |
| Query only affects client UI (filter an already-loaded list) | `useSearchParams()` in a client component |
| Read the query inside an event handler without re-rendering | `new URLSearchParams(window.location.search)` |

### Root params: `next/root-params` (new in 16.3)

Dynamic segments **above the root layout** are *root params*. Example: `app/[lang]/layout.tsx` is the root layout, so `lang` is a root param.

You can read them **from any Server Component** without prop drilling:

```tsx
// src/server/i18n/get-dictionary.ts
import { lang } from 'next/root-params'

export async function getDictionary() {
  const l = await lang()
  return import(`@/locales/${l}.json`).then((m) => m.default)
}
```

Why they are special: the root layout is shared by **every** route under it, so the value is the same everywhere in that tree. Deeper params like `[slug]` mean different things in different branches, so they stay as props.

Rules:

- Server Components only. Not in Client Components, Server Actions, Route Handlers (planned), or `unstable_cache`.
- ⚡ With Cache Components, each root param needs a `generateStaticParams` with at least one value.
- Inside `'use cache'`, only the root params you actually call become part of the cache key. That's better than passing all `params` in.
- Segment names must be valid JS identifiers: `[post-slug]` fails, `[postSlug]` works.

## Tips & tricks

- **Pass `params` promises down, await them deep.** This keeps the outer UI in the static shell. It's the single most useful habit in this project.
- **Prefer `[[...slug]]` for docs/CMS** so the index (`/docs`) and the leaves share one page and one layout.
- **Catch-all + `notFound()`** together make a "smart 404". Look up the path in the CMS, and if it isn't there, call `notFound()`.
- **Template literals in `<Link href>` are type-checked** with `typedRoutes`: `href={`/blog/${slug}`}` is validated against existing routes.
- **Specific beats dynamic.** `app/blog/new/page.tsx` wins over `app/blog/[slug]/page.tsx` for `/blog/new`. You don't need special handling for it.
- **`generateStaticParams` runs on navigation in `next dev`**, and at build time before the pages. During ISR revalidation it is **not** run again.
- **`fetch` inside `generateStaticParams` is memoized** with the same fetches in layouts and pages during the build, so you don't pay twice.

## Pitfalls

| Mistake | Symptom |
| --- | --- |
| `const { slug } = params` (no await) | TypeScript error. At runtime, `slug` is `undefined`. |
| Awaiting `params` at the top of the page/layout without Suspense (⚡, no gSP) | Build error, or a dev "URL data outside of Suspense" insight with Partial Prefetching. |
| `generateStaticParams` returns `[]` (⚡) | Build error: empty generateStaticParams. |
| `export const dynamicParams = false` (⚡) | Not supported with Cache Components. |
| `searchParams.page` used as a number directly | It's `string \| string[] \| undefined`. Parse and validate it. |
| Kebab-case root param folder `[post-slug]` used with `next/root-params` | Error: not a valid identifier. |

## Where it's used

- **Blog/CMS:** `[slug]` + `generateStaticParams` for the top N posts, the rest rendered on demand.
- **E-commerce:** `[category]/[product]`, generated top-down. Facets in `searchParams`.
- **Docs:** `[[...slug]]` mapping to a content tree, with `notFound()` for unknown paths.
- **i18n:** `app/[lang]/layout.tsx` as the root layout + `next/root-params` in translation helpers.
- **Multi-tenant:** `app/[tenant]/...` (often rewritten from a subdomain by `proxy.ts`, see Phase 06).
